# Подписанные обновления LiteChecker

`scripts/release.py` готовит релиз локально и ничего не публикует. Он принимает
обычный архив исходников из `scripts/package_agent.py`, проверяет содержимое и
подписывает метаданные ключом Ed25519. Для загрузки на GitHub предназначены только
проверенный ZIP, `release.json` и публичный `update-channel.json`.

## Ключ автора

Из корня исходников подготовьте окружение командой `uv sync --locked --group dev`.
Один раз создайте пару ключей в отдельной закрытой папке вне репозитория:

```sh
mkdir -m 700 ../litechecker-release-keys
.venv/bin/python scripts/release.py keygen \
  --private-key ../litechecker-release-keys/signing-private.key \
  --public-key ../litechecker-release-keys/signing-public.key
```

Оба файла содержат base64 от сырых 32 байт ключа. Приватный файл создаётся с
правами `0600`, публичный — `0644`; существующие файлы и символические ссылки не
перезаписываются. Приватный ключ не выводится в терминал. Храните его резервную
копию отдельно от исходников и дистрибутивов. Инструмент читает ключ только из
файла `--private-key`; значение ключа не нужно передавать в аргументах команды.

Публичный ключ передаётся первому устройству доверенным способом. Обычное
обновление не меняет установленный ключ или адреса канала. При утрате ключа
нельзя продолжить подпись тем же ключом; смена доверия требует отдельного
доверенного обновления настроек устройств.

## Подготовка релиза

Сначала выполните полностью локальную проверку `scripts/verify-release.sh offline`.
Она не обращается к Docker и не запускает реальные probes. Отдельный
`scripts/verify-release.sh live` — явная финальная проверка с Docker и настоящим
smoke-запросом; запускайте её только в разрешённом окружении перед публикацией.

Ниже `OWNER/REPO` — заполнитель: укажите существующий выбранный репозиторий.
Релиз должен быть доступен клиентам по HTTPS без GitHub PAT. У клиентов нет
учётных данных автора и доступа к приватному ключу.

1. Установите новую версию `major.minor.patch` в `pyproject.toml` и выполните
   проверки проекта. Версия не содержит префикса `v`, ведущих нулей или суффикса.
2. Выберите `sequence`, строго больше номера всех предыдущих выпущенных релизов.
   Например, следующая публикация после `2` использует `3`. Инструмент работает
   без сети и не знает историю GitHub; проверить номер обязан автор релиза.
3. Перед первой упаковкой создайте публичный файл канала в корне исходников.
   Команда использует только публичный ключ и отказывается перезаписывать файл:

```sh
.venv/bin/python scripts/release.py channel \
  --public-key ../litechecker-release-keys/signing-public.key \
  --repository OWNER/REPO \
  --output update-channel.json
```

Упаковщик включает этот файл и в публичный ZIP, и в приватный архив первой
установки. Получателю достаточно одного установочного архива. Если канал уже
создан для этого ключа и репозитория, используйте существующий файл.

4. Соберите публичный архив и подпишите его. Для каждого релиза используйте новую
   папку результата:

```sh
.venv/bin/python scripts/package_agent.py
.venv/bin/python scripts/release.py build \
  --archive dist/LiteChecker-agent.zip \
  --version 0.3.0 \
  --sequence 3 \
  --repository OWNER/REPO \
  --private-key ../litechecker-release-keys/signing-private.key \
  --output dist/releases/0.3.0
```

Порядок первой подготовки: `keygen` → `channel` → упаковка → `build`.
Версия внутри ZIP обязана совпасть с `--version`. Встроенный канал, если он
есть, обязан содержать тот же публичный ключ, которым проверяется подпись.
Перед записью результата
проверяются внутренний `CONTENTS.sha256.json`, хеш каждого файла, допустимые
пути, типы файлов и лимиты архива. Архивы `PRIVATE`, секреты, состояние,
рабочие `.env`, установленные среды выполнения и повреждённые ZIP отклоняются.
Переименование приватного архива не делает его публичным. Обнаруженный ключ
подписи даже в обычном файле исходников также блокирует выпуск.

Результат содержит ровно три файла:

| Файл | Назначение |
| --- | --- |
| `LiteChecker-0.3.0.zip` | Неизменённые байты проверенного публичного архива |
| `release.json` | Версия, sequence, время UTC, HTTPS-адрес ZIP, размер, SHA-256 и подпись Ed25519 |
| `update-channel.json` | Публичный ключ и постоянный адрес подписанных метаданных для первой установки |

Существующие результаты не перезаписываются, включая символические ссылки.
Для повторной подготовки используйте новую пустую папку. Не заменяйте уже
опубликованные байты ZIP или метаданных: исправление выпускается с новой
версией и большим `sequence`.

## Публикация и первое устройство

В GitHub создайте черновик Release с тегом `v0.3.0`, соответствующим проверенным
исходникам. Загрузите три файла из `dist/releases/0.3.0`, проверьте имена и затем
опубликуйте релиз как latest. ZIP будет находиться по адресу:

```text
https://github.com/OWNER/REPO/releases/download/v0.3.0/LiteChecker-0.3.0.zip
```

Постоянный адрес метаданных:

```text
https://github.com/OWNER/REPO/releases/latest/download/release.json
```

Подготовьте сначала одно тестовое устройство. Передайте ему доверенный
установочный архив с уже включённым `update-channel.json` и сверьте публичный
ключ с сохранённым `signing-public.key`. Файл канала используется только если
локальная конфигурация доверия ещё не создана. Само скачивание нового файла
канала не является разрешением заменить уже установленный ключ.

Приватные параметры первой установки — Telegram, подписка и необязательный
Telegram-прокси — передаются в приватном установочном архиве. Архивы
`LiteChecker-READY-PRIVATE.zip` никогда не загружается в GitHub Releases. Команда
`TRY-DIRECT.command` уже входит в этот единый PRIVATE-архив. Обновления не
переносят секреты и не заменяют
конфигурацию, идентификатор устройства или накопленные отчёты.

На первом устройстве проверьте статус настройки канала, установку следующей
подписанной версии и сохранность его настроек. Отдельно проверьте, что обновление
остановленного пользователем checker не запускает его. После успешной проверки
передавайте ту же доверенную конфигурацию канала остальным устройствам. Без
настроенного канала автоматическое обновление остаётся выключенным.

Резервный HTTPS-адрес может отдавать те же подписанные байты. Отказ сети или
неверная подпись оставляет рабочую версию. При неудачной активации используется
предыдущая рабочая версия; штатная очистка сохраняет текущую и одну предыдущую
управляемую версию. Для возврата к старому коду после успешного релиза выпустите
его как новую версию с большим `sequence`: старые подписанные метаданные не
должны обходить защиту от повтора.

## Что именно подписывается

Подпись покрывает UTF-8-представление `payload`, полученное строго так:

```python
json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=True)
```

Конверт содержит только `schema: 1`, `payload` и base64-подпись длиной 64 байта.
Публичный ключ длиной 32 байта берётся из доверенной локальной настройки.
Подпись проверяется повторно перед записью результата. Ограничения: метаданные
64 КиБ, ZIP 32 МиБ, распакованные файлы 128 МиБ, не более 2048 записей. SHA-256
связывает подпись с точными байтами ZIP; отдельная неподписанная контрольная
сумма не заменяет подпись.

Автоматический workflow публикации пока не добавлен. Выпуск и загрузка в
GitHub выполняются автором явно после проверки результатов.
